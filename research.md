## Official status: Roon on Linux (as of 2026-08-01)

*Confidence: high*

**Summary.** As of August 2026 there is still no official native Linux GUI client for Roon, and none has been announced: the canonical community feature-request thread remains tagged "[not on roadmap, you may try to use Wine]", the last clear staff statement (Danny Dulai, 2019) cited demand "well below the effort needed", and Roon's official Linux install docs still list only Roon Server and Roon Bridge. Current production software is Roon 2.70 (build 1671, released 2026-07-07) with ARC 1.80; Early Access is at 2.71 build 1676 / ARC 1.81 build 423. The big 2026 story is a platform migration to .NET 10 (Roon 2.65, 2026-04-27) that raised minimum requirements (Linux: glibc 2.27+, OpenSSL 1.1.1+) and introduced an official Docker image as the recommended Linux deployment; 2.70 also swapped search to the Rust-based Tantivy engine. Under Harman (acquired Nov 2023) I found no API deprecations, no new developer terms, and pricing unchanged since the Jan 2023 increase — the JS Roon API is still public on GitHub under Apache 2.0 but appears dormant, and a community Flutter+Rust app ("Community Remote", MIT) already ships a native Linux GUI via Flathub, though constrained by what the extension API exposes. Linux users today rely on roon-on-wine (still maintained), Windows VMs, official mobile apps, web-controller extensions, or Community Remote.

## The official extension API (protocols, capabilities, limits)

*Confidence: high*

**Summary.** The official Roon extension API (github.com/RoonLabs/node-roon-api plus per-service repos) is a JavaScript client for two proprietary protocols: SOOD, a UDP discovery protocol on port 9003 (multicast 239.255.90.90), and MOO, a text-header RPC protocol carried over a WebSocket to the Core (TCP, typically in the 9100-9200 range). There is no standalone protocol spec — the implementations plus JSDoc are the documentation — but the protocols are simple and have been reimplemented in Python (pyroon), Rust (roon-api crate) and TypeScript (roon-kit). Authorization is a user-approval flow: the extension announces identity metadata, the user clicks Enable in Settings > Extensions, and a token is persisted by the extension for reconnects. The API covers transport control (play/pause/seek/volume/mute/standby), zone grouping/transfer, zone+queue subscriptions, a server-side-session Browse hierarchy (library, playlists, internet radio, search) and image fetching — but cannot edit the queue (beyond play_from_here), configure DSP, edit library metadata, change Roon settings, read the signal path, or fetch lyrics. Repo activity is minimal-but-alive: last commit to node-roon-api was Feb 3, 2026 (merged by Roon co-founder Danny Dulai), the service repos have been dormant since 2016-2020, yet a July 2026 Early Access regression that broke extension browsing was fixed by Roon staff within ~48 hours, showing the API is still supported under Harman ownership. Everything is Apache-2.0 licensed with no additional usage terms found in the repos.

- **MOO is a text-header RPC protocol over WebSocket: messages start with 'MOO/1 REQUEST <name>' (or verbs CONTINUE/COMPLETE), carry Request-Id, Content-Length and Content-Type headers, and JSON bodies; responses are matched to requests by Request-Id and COMPLETE finalizes a request.**
  Confirmed directly from moo.js source on master: body = Buffer.from(JSON.stringify(body)) with content_type 'application/json'; parser assumes 1 WebSocket frame == 1 MOO message (changelog note: parsing was simplified because the API is websockets-only). Subscriptions are long-lived requests receiving CONTINUE messages until COMPLETE.
  — Source: <https://github.com/RoonLabs/node-roon-api/blob/master/moo.js> (master branch, checked 2026-08-01)

- **SOOD discovery uses UDP port 9003 with multicast group 239.255.90.90: binary messages with magic 'SOOD', version byte 2, type 'Q' (query) or 'R' (response), followed by length-prefixed key/value properties including a _tid UUID transaction id.**
  Confirmed from sood.js source: SOOD_PORT=9003, SOOD_MULTICAST_IP='239.255.90.90'; queries are sent via multicast, broadcast and unicast; the implementation rescans network interfaces every 5 seconds and honors _replyaddr/_replyport overrides. After discovery, the Core is reached over TCP (Roon uses 9100-9200 for Core communication per community/port documentation), which is why browsers must use ws_connect({host, port}) with a manually entered address instead of UDP discovery.
  — Source: <https://github.com/RoonLabs/node-roon-api/blob/master/sood.js> (master branch, checked 2026-08-01; port-range info from community posts (older but consistent))

- **There is no official standalone protocol specification; the API is documented only via the node-roon-api implementation and its JSDoc site, and the README labels the API as 'beta'.**
  JSDoc is hosted at roonlabs.github.io/node-roon-api. A native Linux client would implement SOOD+MOO from these sources or reuse a third-party port (pyroon for Python, roon-api Rust crate 0.5.x with roon-cli/roon-mcp companions, roon-kit TypeScript wrapper) — evidence the protocol is fully implementable outside Node.js. This is a confirmed fact about documentation status; the feasibility judgment is inference.
  — Source: <https://roonlabs.github.io/node-roon-api/RoonApi.html> (JSDoc current with repo; Rust crate and roon-kit verified active via crates.io and community posts, 2025-2026)

- **Pairing/authorization: the extension declares identity metadata (extension_id, display_name, display_version, publisher, email, website) in the RoonApi constructor; the user must click Enable in Settings > (Setup >) Extensions; the granted token is persisted by the extension via save_config/load_config (config.json by default, overridable via get/set_persisted_state).**
  Two connection models: recommended pairing mode (core_paired/core_unpaired callbacks, one Core at a time, Roon shows a 'Pair' button to switch Cores) and non-pairing mode (core_found/core_lost, sees every discovered Core, no Pair button). Extensions that consume no Roon services are authorized automatically; anything using transport/browse/image requires the explicit user Enable step. Confirmed from README and JSDoc.
  — Source: <https://github.com/RoonLabs/node-roon-api/blob/master/README.md> (master README, checked 2026-08-01)

- **Transport service (com.roonlabs.transport:2) capabilities: control (play/pause/playpause/stop/previous/next), seek (absolute/relative), change_volume (absolute/relative/relative_step per output, honoring dB/step scales), mute/mute_all, standby/toggle_standby/convenience_switch, group_outputs/ungroup_outputs, transfer_zone, change_settings (shuffle, auto_radio, loop/loop_one), subscribe_zones/subscribe_outputs/subscribe_queue(max_item_count), get_zones/get_outputs, and play_from_here(queue_item_id).**
  Confirmed from RoonApiTransport JSDoc and lib.js source. Zone objects carry state plus now_playing with one_line/two_line/three_line display text, image_key, seek_position and length; queue items carry queue_item_id. This is sufficient for a full now-playing + remote-control UI including zone grouping and live queue display.
  — Source: <https://roonlabs.github.io/node-roon-api/RoonApiTransport.html> (JSDoc + repo source, checked 2026-08-01 (repo last updated Jun 2020 but verified working against 2026 Roon builds per community threads))

- **Browse service capabilities: stateful server-side browse sessions over hierarchies 'browse' (general library incl. streaming content), 'playlists', 'internet_radio', 'albums', 'artists', 'genres', 'composers', 'search', and a limited 'settings' hierarchy; browse() drills in via item_key, takes 'input' for search text, pop_all/pop_levels for navigation, and zone_or_output_id to enable play actions; load() paginates items (default 100).**
  Confirmed from RoonApiBrowse JSDoc. Result actions are list/message/replace_item/remove_item/none. Playing music is done by drilling into action items (e.g. 'Play Now') rather than direct play-by-id calls — meaning a native client's browse UI must be list-driven, mirroring Roon's session model, rather than a free-form media database query API.
  — Source: <https://roonlabs.github.io/node-roon-api/RoonApiBrowse.html> (JSDoc current, checked 2026-08-01)

- **Other services: image (fetch album/artist artwork by image_key with scaling), plus extension-provided services status (report state to Roon), settings (render an extension settings UI inside Roon), volume-control and source-control (surface external hardware volume/source into Roon); a newer audioinput API (repo created ~2023) lets an extension feed audio/stream URLs into Roon for playback.**
  Service list confirmed from the README and the RoonLabs org repo listing (node-roon-api-image, -status, -settings, -volume-control, -source-control, -audioinput). The audioinput path is what Roon staff/community point to for playing external stream URLs, since the queue cannot be injected into directly (Bandcamp extension thread, Mar-Apr 2025).
  — Source: <https://github.com/orgs/RoonLabs/repositories?q=node-roon-api> (org listing checked 2026-08-01)

- **Hard limitations vs the native client (confirmed): no queue editing beyond play_from_here (no add/remove/reorder — extension authors maintain shadow queues as a workaround), no DSP control of any kind, and Roon ARC zones are invisible to the extension API.**
  Queue: community thread 'Roon API support for zone queue manipulation' (Mar 31-Apr 2, 2025) — 'You can't add stream URLs to the Queue.' DSP: 'Controlling DSP via API?' thread — 'At the moment the API doesn't incorporate any DSP functionality' (old thread, ~2018, but no DSP endpoints exist in any service repo today, so still true). ARC: feature suggestion 'ARC zone not visible in Extension API' (2026).
  — Source: <https://community.roonlabs.com/t/roon-api-support-for-zone-queue-manipulation/296570> (threads from 2025 and 2026; DSP thread from ~2018 corroborated by current repo contents)

- **Further limitations (confirmed by absence from the entire API surface, i.e. inference from primary sources): no library/metadata editing, no Roon settings management (audio device setup, storage, users), no initial Core setup/login, no signal path data (zone objects contain no signal-path fields), and no lyrics endpoints.**
  The full service list is transport, browse, image, status, settings(extension-own), volume-control, source-control, audioinput — nothing else exists in the RoonLabs org. Community extensions that show signal path or lyrics get that data elsewhere (e.g. RoonPresence reads HQPlayer's own API for signal path; lyrics extensions use external lyrics providers). Consequence for the project brief: a community Linux client built on this API can be a full-featured remote/browser/now-playing app but can never replace the native client for setup, DSP, or library management.
  — Source: <https://github.com/orgs/RoonLabs/repositories?q=node-roon-api> (checked 2026-08-01; classification as inference-from-absence, not a staff statement)

## Third-party ecosystem and prior art

*Confidence: high*

**Summary.** The Roon third-party ecosystem splits cleanly into two layers. Nearly everything that exists today — roon-tui, Community Remote, pyroon/Home Assistant, roon-web-controller and its successor roon-web-stack, rooExtend, RoonCommandLine — is built on Roon Labs' official, deliberately-sandboxed extension API (node-roon-api: SOOD discovery + MOO/1 text protocol over WebSocket on TCP 9330, Apache-2.0). That API is in maintenance-only mode (no new services since ~2018; recent commits are third-party dependency/security PRs) and its ceiling is well documented by the authors who hit it: Community Remote's developer states plainly "the functionality that can be provided is limited by the Roon API" (no queue clearing, no metadata editing, no library management). The far bigger 2026 development is arthursoares/roon-api-reverse-engineering (June–July 2026, MIT): the first public reverse-engineering of Roon's NATIVE desktop-client-to-Core protocol — `Sooloos.Broker.Remoting`, raw binary TCP on port 9332 — achieved not by packet-guessing but by decompiling Roon's unobfuscated Mono/.NET assemblies with ilspycmd, yielding all ~1550 method signatures; it reports no authentication on the local network and demonstrated playback, favoriting and metadata editing. Roon CTO Brian Luczkiewicz responded publicly on 2026-06-23 that Roon does not object to interoperability tinkering but warns the protocol changes freely and that misuse can leak memory/compute inside the Core. RAAT, by contrast, remains completely closed — licensed only under the Roon Ready certification program, never reverse-engineered publicly, and explicitly declared out of reach by Music Assistant's maintainer in March 2026 — so a Linux GUI can control playback but cannot itself be an audio endpoint without Roon Bridge. Roon Labs reconfirmed as recently as 2025-09-19 that no Linux GUI exists and Wine is the suggested workaround.

- **The native Roon desktop-client-to-Core protocol was publicly reverse-engineered for the first time in June–July 2026, and the results are published under MIT license.**
  arthursoares/roon-api-reverse-engineering (repo created 2026-06-24, last push 2026-07-17, MIT, ~14k LOC TypeScript). It targets `Sooloos.Broker.Remoting` on raw TCP port 9332 with binary framing and varints — explicitly contrasted in the README with the public extension API on port 9330 (text MOO/1 over WebSocket, pairing-based auth). Headline claims: (1) "on the local network the protocol doesn't seem to use any authentication" — no cloud token needed for mutations; (2) object references are ephemeral session handles, so the model is "browse-then-mutate", not authenticate-then-mutate; (3) typed wrappers generated for all ~1550 methods but "only a handful have been run live"; (4) hand-verified against one Core: read object graph, favorite, play (real audio), pause, standby/power, and a reversible metadata edit — the last being impossible via the public API. Author states it is a proof-of-concept, not a product, and "not affiliated with or endorsed by Roon Labs". Repo layout includes packet captures, an oracle/golden-test harness, and an Astro/Starlight docs site.
  — Source: <https://github.com/arthursoares/roon-api-reverse-engineering> (repo pushed 2026-07-17; created 2026-06-24)

- **The breakthrough technique was decompiling Roon's unobfuscated Mono/.NET client assemblies, not packet analysis — this is the single most actionable lesson for anyone building a native Linux client.**
  The project's write-up states the critical breakthrough was running `ilspycmd` against Roon's client assemblies, which "transformed the work into more of a porting job than pure reverse-engineering" and yielded complete protocol specs plus all ~1550 method signatures directly from type metadata. Reported pitfalls: the protocol drops malformed AND unauthorized calls identically with no error code, which sent the author down a false 'cloud auth token required' rabbit hole when the real cause was stale handles; and session-scoped object handles from old captures silently point at nothing in new connections. Advice given: prioritize source inspection over byte-level brute-forcing, and separate persistent identifiers from session handles early. Remaining unsolved: full streaming-catalog (Tidal/Qobuz) search, which returns results via lazy reactive follow-up queries not yet decoded. Work was done pair-programming with Claude Code.
  — Source: <https://arthursoares.github.io/roon-api-reverse-engineering/journey/> (docs site, 2026-07)

## Audio path: Roon Bridge, RAAT, and alternatives

*Confidence: high*

**Summary.** Roon Bridge remains the only sanctioned bit-perfect audio path for a Linux Roon client: it is officially distributed for Linux x64, armv7hf, and armv8 via shell-script installers or tarballs from download.roonlabs.com, and it is actively maintained in 2025/2026 (build 1501/version 2.60 shipped after a Feb 2026 security re-signing, and Roon has announced a .NET 10-based Bridge with Early Access in July 2026 and production planned for August 30, 2026). Roon officially supports only exclusive ALSA hw:X,X access and explicitly does not support PulseAudio/PipeWire, so on modern desktops users resort to workarounds: pointing Bridge at the "plug:pipewire" or "pulse" ALSA PCM (requires running Bridge as the desktop user instead of root), or an snd-aloop loopback re-routed into PipeWire. Roon's Terms & Conditions prohibit copying, redistribution, sublicensing, and reverse engineering without prior written consent, so a third-party app must have users download Roon Bridge from Roon's servers (the pattern the AUR package follows) rather than bundling it. No open-source RAAT implementation exists — the Music Assistant project concluded in March/April 2026 that "RAAT is fully closed source and we simply can not implement it" — and Roon Ready certification is a commercial hardware program involving SDK licensing, Roon source-code review, hardware samples, and sign-off at Roon Labs' discretion. Sanctioned non-RAAT fallbacks reachable from Linux are AirPlay (shairport-sync works but Roon caps AirPlay at 16/44.1), Chromecast (up to 24/96 on audio-only devices, 48 kHz on video Chromecasts), and Squeezebox emulation via squeezelite (works in practice but Roon officially states software Squeezebox implementations are unsupported and untested).

- **Roon Bridge is officially available for Linux on x64, armv7hf, and armv8 (aarch64), installed via an 'easy installer' shell script or manual tarball from download.roonlabs.com/builds/, with no login or click-through required to download.**
  Official Linux install guide lists Roon Server (x64 only) and Roon Bridge (x64/armv7hf/armv8). Easy installer: curl roonbridge-installer-linuxx64.sh (or ...armv7hf/...armv8) and run as root; manual install extracts a tarball, needs libasound2 >= 1.0.27, glibc 2.14+, and a systemd unit; ffmpeg is required only for Roon Server, not Bridge. Guide states there is no purpose running Bridge and Server on the same machine since both expose the same audio devices. Confirmed fact from official docs.
  — Source: <https://help.roonlabs.com/portal/kb/articles/linux-install> (official KB page, current as fetched 2026-08)

- **Roon Bridge still receives updates in 2025/2026, though infrequently: current production build is 1501 (version string 2.60), and a major .NET 10 rebuild is scheduled for production on August 30, 2026.**
  Timeline: Bridge sat on 1.8 build 1125 for years (NixOS still packages 1.8-1125 per Repology, AUR packages 2.60.1501). Feb 2025: build 1496 briefly pushed as '2.0' then reverted (community thread 293640). Roon's official 'Current Production Versions' thread lists Roon Bridge build 1501 for Linux/macOS/Windows. Feb 2026: out-of-cycle security update to version 2.60, described by community members as 'probably functionally identical to the previous 1.8 release' — mainly a new signing mechanism. Official announcement: on 2026-08-30 Roon Bridge moves to .NET 10 (Early Access from July 2026); new Linux minimums will be glibc 2.27+ and OpenSSL 1.1.1+. Confirmed facts; as of today (2026-08-01) the .NET 10 build is in Early Access.
  — Source: <https://community.roonlabs.com/t/important-roon-bridge-minimum-system-requirements-are-changing-on-august-30-2026/322567> (official Roon announcement thread, mid-2026; corroborated by https://community.roonlabs.com/t/roon-bridge-latest-update/315534 (Feb 2026), https://community.roonlabs.com/t/roon-2-0-current-production-versions/213416, https://repology.org/project/roon-bridge/versions)

- **Roon officially supports only direct, exclusive ALSA hardware access on Linux ('hw:X,X'); PulseAudio and PipeWire are not supported output paths.**
  Official 'Audio on Linux' doc: 'we only support situations where we have direct and exclusive access to the hardware (in ALSA terms, we are using hw:X,X device identifiers).' Native DSD requires ALSA lib 1.0.29+. Consequence on desktops: Roon Bridge's exclusive claim on the sound card conflicts with PipeWire/PulseAudio (community threads 'Roon Bridge on Linux disables audio', 'Pulseaudio support for Roon'). A Roon Bridge instance is auto-discovered by Roon Server over the LAN and its enabled ALSA devices appear as zones under Settings > Audio grouped by the Bridge host — this zone-appearance detail is standard Roon behavior described across community docs rather than in the pages fetched (low-risk inference).
  — Source: <https://help.roonlabs.com/portal/en/kb/articles/audio-on-linux> (official KB page, current as fetched 2026-08)

- **The main working PipeWire-coexistence trick in 2026 is configuring Roon Bridge's ALSA output device to 'plug:pipewire' and running Bridge as the desktop user instead of root; the older trick is an snd-aloop loopback re-routed into the default sink.**
  March 2026 blog walkthrough (Schiit Jotunheim + Roon Bridge + PipeWire): Roon Bridge runs as root by default while PipeWire runs per-user, so a systemd override runs Bridge as the logged-in user with the right XDG environment; the device is set to 'plug:pipewire' ('wraps PipeWire in ALSA's plug layer'), software volume in Roon replaces the missing ALSA mixer, and UDP ports 30000-65535 must be open for RAAT clock sync or tracks skip. Alternative (Aug-Nov 2024 community thread, Arch + PipeWire/WirePlumber): modprobe snd-aloop, point Bridge at the loopback hw:2,0,0 and route to the default sink with GStreamer — author called it 'quite hacky' and later abandoned Roon on Linux; another user suggested squeezelite as simpler. There is also an ALSA 'pulse' plugin route mentioned in the 'Roon bridge and pulseaudio on linux' thread (162622). ## UI stack options for Linux in 2026

*Confidence: high*

**Summary.** For a GPU-accelerated, artwork-heavy Linux music client in 2026, every serious precedent app ships web tech (Plexamp, Feishin, tidal-hifi are Electron; Spotify uses CEF), while the polished native precedents split between GTK4/Rust (Amberol), Qt/QML-Kirigami (Elisa), and Go/Fyne (Supersonic). Flutter desktop got a major credibility boost in May 2026 when Canonical became lead maintainer of the desktop embedders and Flutter 3.44 shipped multi-window, but Linux rendering still uses Skia/OpenGL via a GTK3 embedder (Impeller/Vulkan for Linux is only at design-doc stage) and fractional-scaling behavior under Wayland is the main open question. Qt 6 is the most technically complete option (LGPLv3 core, first-class Wayland fractional-scale-v1 support, GPU scene graph, mature GridView virtualization in QML); GTK4 is close behind (Vulkan renderer default on Wayland since 4.16, recycling GtkGridView built for huge grids). Tauri v2 is the riskiest for this use case: its Linux webview is WebKitGTK, whose DMABUF renderer has officially documented blank-window/flicker/crash problems with NVIDIA and silent WebGL software fallback; the Servo/Verso escape hatch is still experimental. Rust-native iced is now production-proven at desktop-environment scale (System76 COSMIC 1.x stable releases through July 2026), while egui's immediate-mode model is a poor fit for large scrolling media libraries by its own documentation; Slint is viable license-wise (royalty-free tier for desktop) but has no notable music-app precedent.

## Critique: gaps and contradictions

A completeness critic reviewed all six research reports before the follow-up round.

### Decision-changing gaps (each answered by a follow-up below)

- **Extension API Browse coverage of streaming content and modern Roon features on current (2.70) builds** — The go/no-go hinges on whether a client built on the official extension API is actually usable for real Roon users. If the Browse/search hierarchies cannot surface TIDAL/Qobuz catalog content, Daily Mixes, or Roon's newer AI/recommendation features on 2026 builds, the client is crippled for the streaming-centric majority regardless of UI quality. The roon-api agent explicitly could not verify this ('classic library tree' vs full coverage), and no agent found concrete 2025-2026 evidence either way.
- **Impact of the .NET 10 Roon Bridge rebuild (production 2026-08-30) on the Linux audio path** — The entire audio half of the proposed architecture is Roon Bridge, and a ground-up .NET 10 rebuild ships to production ~4 weeks from now. Early Access builds have been public since July 2026, so changes to supported CPU architectures (armv7hf?), glibc/OpenSSL floors, installer/tarball URLs, the root-by-default systemd unit, or ALSA device handling (including the 'plug:pipewire' desktop workaround the architecture depends on) are researchable today and could invalidate install-flow and PipeWire-coexistence design decisions.
- **Viability and legal standing of the reverse-engineered native protocol (port 9332) as a gap-filler beyond the extension API** — The extension API's ceiling (no queue editing, no DSP, no signal path) is confirmed and hard, so the only known route toward feature parity is the June-July 2026 reverse-engineered native protocol. Whether the architecture should stay pure-extension-API or plan a hybrid depends on whether that protocol still works against post-July-2026 builds and whether using it is legally tenable — and the legal agent's analysis predates this development entirely (it claims no such precedent exists), so its risk assessment cannot be relied on.

### Contradictions between researchers

- Extension API connection port: the roon-api agent says the MOO WebSocket to the Core runs on 'TCP, typically in the 9100-9200 range', while the ecosystem agent states it runs on 'TCP 9330' (and puts the native protocol on 9332). Both cannot be the current behavior as stated; likely a version difference neither agent identifies. This must be resolved (does the SOOD response advertise the port on 2.70 Cores?) before the connection layer is designed.
- Native-protocol reverse-engineering precedent: the legal agent claims 'no public attempt was found, so there is no precedent either way' for reverse-engineering the native client-to-Core protocol, but the ecosystem agent documents exactly such a public project (arthursoares/roon-api-reverse-engineering, June-July 2026) including a public, non-objecting response from Roon's CTO. The legal agent's risk analysis rests on a premise another agent disproves and must be redone against the actual precedent.
- Recency of Roon's 'no Linux GUI' position: official-status says the last clear staff statement dates to 2019 (Danny Dulai) and lists any post-2021 statement as an open question, while ecosystem cites a staff reconfirmation on 2025-09-19 (thread 306706). The 2025 statement resolves official-status's open question and should supersede its framing — minor, but it firms up the premise that no official client is coming.

## Follow-up: Viability and legal standing of the reverse-engineered native protocol (port 9332) as a gap-filler beyond the extension API

*Confidence: medium*

Arthur Soares announced it 2026-06-18 and made the MIT-licensed TypeScript repo public on 2026-06-24 after Roon co-founder/CTO Brian Luczkiewicz (username 'brian') replied on 2026-06-23. - **ANALYSIS (inference, not a sourced fact): the legal picture is more favorable than a 'no precedent' framing, but Section 2.1's 'substantially similar' condition and NY governing law impose real limits.**
  (a) EU Software Directive Art. 6 permits decompilation for interoperability of an independently created program; Art. 8 makes this right non-overridable by contract, so Roon's Section 2.1 cannot lawfully forbid genuine interoperability RE in the EU. (b) US DMCA 1201(f) permits RE for interoperability, but 1201 only bites if a technological protection measure was circumvented; the project reports NO authentication/encryption and unobfuscated assemblies, so likely no TPM triggers 1201 at all — consistent with Brian's 'unless encryption was broken.' (c) Biggest contractual risk: Section 2.1 forbids using results to create software 'substantially similar to the Roon Software'; a native Linux GUI replicating Roon's desktop UI/features could be argued to breach this, and NY law/NY courts govern (Section 19), where contractual RE bans are more enforceable than the EU carve-out. A Linux GUI built for a distinct purpose (a Linux client where none exists) is defensible but must avoid cloning Roon's software.
  — Source: <https://roon.app/en/termsandconditions> (analysis as of 2026-08-01)
